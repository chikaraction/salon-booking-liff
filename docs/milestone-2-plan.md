# Milestone 2: 客側予約フロー(LIFF)+ 空き枠計算ロジック

- 日付: 2026-07-16
- 参照ADR: ADR-002(通知チャネル)/ ADR-003(LINEログイン)/ ADR-004(EXCLUDE制約)/
  ADR-006(デザインシステム)/ ADR-007(店舗固有値をコードに書かない)

## スコープ

客がLIFFアプリから予約を完了できるところまで。

1. **空き枠計算ロジック**(`src/lib/` 純粋関数、テストファースト)
2. **予約フローUI**: メニュー選択 → スタッフ選択 → 日時選択 →(初回のみ情報入力)→
   予約確認 → 予約完了
3. **LINEログイン(LIFF)**: IDトークンのサーバー側検証で顧客を特定。
   初回は名前・電話番号を入力して顧客レコード作成、2回目以降は入力不要(ADR-003)
4. **予約の保存**: EXCLUDE制約違反(23P01)を捕捉して「その枠は埋まりました」
   と表示し日時選択へ戻す(ADR-004)
5. **予約ポリシーのDB化**: 枠の刻み・受付期間・直前締切を `salon_settings` に
   追加するマイグレーション(ADR-007: コードに書かない)

### スコープ外

- マイ予約・キャンセル・変更(M3)
- 管理画面(M4)
- LINE応答メッセージ・前日リマインド送信(M5)。完了画面の
  「確認のメッセージをLINEにお送りしました」文言はM5まで表示しない
- Cloudflareデプロイ(M6)。**そのためLIFFの実機確認(LINEアプリ内での動作)は
  デプロイ後に verify-booking で行う。** M2の動作確認は通常ブラウザ+開発用スタブで行う

## 対象画面

`docs/mockups/客側-LIFF(スマホ縦)/` の 01〜06 のスクリーンショットを正とする
(07 マイ予約はM3)。読み取れる実装要件:

- ウィザード形式(STEP 1/4 表示。ステップ = メニュー・スタッフ・日時・確認。
  初回情報入力はステップ数に含めない)。選択済みの内容(メニュー・スタッフ・日時)を
  画面上部にチップで常時表示
- メニューはカテゴリごとにグループ表示(カテゴリ名+説明文)・複数選択可。
  「※ 表示価格は税込です」の注記。選択中の件数・合計金額・合計所要時間+
  「次へ」を画面下部に固定表示
- スタッフ選択は「オーナー/スタッフ/どちらでも」の3択(写真枠+一言紹介。
  写真がなければ頭文字のサークル表示)
- 日時選択はカレンダーで日付 → その日の開始時刻をボタン一覧。
  **埋まっている時刻は取り消し線付きグレーで表示**(選択不可)。勤務時間・
  所要時間の関係で構造的に確保できない時刻や直前締切を過ぎた時刻は表示しない
  (「※ 所要◯分の枠が確保できる時間のみ表示」)
- 予約確認に「ご要望・ご相談(任意)」の自由記入欄 → `reservations.note` に保存
- 初回情報入力は名前・電話番号の2項目(確認画面の前に挟まる)

## データモデルへの影響

スキーマ本体(M1)は変更しない。追加のみ:

### 1. 予約ポリシー列(`salon_settings`)

店舗固有の運用値なのでコードに書かずDBへ(ADR-007)。管理画面での編集はM4。

| 列                      | 型      | default | 意味                                 |
| ----------------------- | ------- | ------- | ------------------------------------ |
| `slot_interval_minutes` | integer | 30      | 空き枠の開始時刻の刻み               |
| `booking_window_days`   | integer | 30      | 何日先まで予約を受け付けるか         |
| `min_lead_minutes`      | integer | 60      | 開始何分前まで予約できるか(直前締切) |

### 2. メニューカテゴリの実体化(`menu_categories`)

| 列              | 型      | 意味                             |
| --------------- | ------- | -------------------------------- |
| `id`            | uuid    | PK                               |
| `name`          | text    | カテゴリ名(自由入力: ADR-007)    |
| `description`   | text    | 客側に表示する説明文(nullable)   |
| `display_order` | integer | 並び順(店側の編集ダイアログはM4) |

`menus.category`(text)は `category_id`(FK)に置き換える。seedも更新する。

### 3. 予約作成RPC(`create_reservation`)

supabase-js は複数文のトランザクションを張れないため、
「顧客の作成/特定 → `reservations` INSERT → `reservation_menus` INSERT(スナップショット)」
を1つのDB関数にまとめる。EXCLUDE制約違反はそのまま呼び出し元へ伝搬させ、
Server Action が SQLSTATE 23P01 を「枠が埋まりました」エラーに変換する。
呼び出しは service_role のみ(ADR-003: 客の操作はサーバー経由)。

マイグレーションはPGlite(btree_gist + authスタブ)で事前検証してから
`npx supabase db push` する(Dockerなし環境の手順)。

## 空き枠計算ロジック(`src/lib/availability.ts`)

純粋関数。DB・DOM・Supabaseクライアントのimport禁止。テストファースト。

```
入力: 対象日 / 所要時間(分) / その曜日の営業時間 / 休業日判定(M2は定休曜日のみ。
      M4で第◯曜日・祝日・指定日ルールが同じ入力に載る) / スタッフの勤務パターン
      (休憩含む) / その日の確定済み予約・ブロックの時間範囲 / 予約ポリシー / 現在時刻
出力: 開始時刻の候補リスト(スタッフごと)。各候補は 空き | 埋まり の状態を持つ
      (モック準拠: 埋まりは取り消し線表示、構造的に不可な時刻はリストに含めない)
```

計算手順:

1. 営業時間 ∩ スタッフ勤務時間 から休憩を除いた「勤務区間」を作る(休業日なら空)
2. 開始候補 = 営業開始〜(営業終了 − 所要時間)を `slot_interval_minutes` 刻みで列挙
3. `[開始, 開始+所要時間)` が勤務区間に完全に含まれる候補だけ残し、
   既存の確定済み予約・ブロックと重なるものは「埋まり」、それ以外を「空き」とする
4. `現在時刻 + min_lead_minutes` より前に始まる候補、`booking_window_days` を
   超える日付は除外(リストに含めない)
5. 「どちらでも」= 各スタッフの結果の和集合。予約時の担当割当は
   **空いているスタッフのうち `display_order` が小さい方**(決定的で説明しやすい)

時刻の扱い: 営業時間・勤務時間は店舗ローカル(JST)の壁時計時刻、予約は
`tstzrange`(UTC)。日本はDSTがないため「JST = UTC+9固定」で純粋関数内で変換する。
カレンダー(月表示)は定休日と受付期間外のみ無効化し、空き有無の日別判定は
日付選択時に計算する(月全体の空き計算はM2ではやらない)。

このロジックはUX向上のための表示用フィルタであり、最後の砦はEXCLUDE制約(ADR-004)。

## LIFF連携(ADR-003)

- `@line/liff` を追加。クライアントは LIFF 初期化後 `liff.getIDToken()` を
  Server Action に渡すだけ(判断を持たない)
- サーバーは LINE の検証API(`https://api.line.me/oauth2/v2.1/verify`)で
  IDトークンを検証し `sub`(userId)を得る → `customers.line_user_id` で照合。
  未登録なら初回情報入力ステップを挟む
- I/Oを伴うコード(LINE API・Supabase service_role)は `src/server/` に置き、
  `src/lib/` の純粋性を守る
- **開発用スタブ**: `NEXT_PUBLIC_LIFF_STUB=1` のとき LIFF SDK を使わず固定の
  ダミーuserIdで動作させ、通常ブラウザでフロー全体をスモークテストできるようにする
  (本番ビルドでは無効)。実機のLIFF動作はデプロイ後(M6)に verify-booking で確認
- 必要な環境変数: `NEXT_PUBLIC_LIFF_ID` / `LINE_LOGIN_CHANNEL_ID`(検証API用)。
  `.env.example` に追記。LINE Developersでのチャネル+LIFFアプリ作成は
  オーナー側作業(実機確認までに用意されていればよい)

## 実施順序

機能単位で都度コミット。ロジックはテストファースト。

1. 設計文書(本ファイル)→ すり合わせ → コミット
2. マイグレーション: 予約ポリシー列 + `menu_categories`(+seed更新)+
   `create_reservation` RPC(PGliteで検証 → `db push`)
3. `src/lib/availability.ts` — 空き枠計算(テストファースト)
4. `src/lib/booking.ts` — 合計金額・合計所要時間の計算、初回入力の
   バリデーション、23P01判定などの純粋ロジック(テストファースト)
5. LIFFラッパー+開発用スタブ、IDトークン検証(`src/server/line.ts`)
6. Server Action: 空き枠取得(所要時間はサーバーでメニューから再計算し、
   クライアントの申告を信用しない)/ 予約作成(23P01 → 「枠が埋まりました」)
7. UI(モック準拠・1画面ずつ): メニュー選択 → スタッフ選択 → 日時選択 →
   初回情報入力 → 予約確認 → 予約完了
8. 検証(下記)

## 検証方法

- `npm test`: 空き枠計算・booking純粋ロジックのユニットテスト
  (境界: 営業時間端・休憩またぎ・既存予約と隣接[半開区間なので接触はOK]・
  直前締切・受付期間外・定休日・「どちらでも」の和集合と割当)
- `npm run build` / `npm run lint`
- ブラウザスモーク: LIFFスタブモードで メニュー→…→完了 を通し、
  Supabase上に `reservations` + `reservation_menus` が正しく入ることを確認。
  同じ枠への2重予約をUIから試み「枠が埋まりました」表示を確認
- EXCLUDE制約の同時INSERT競合・LIFF実機・レスポンシブは verify-booking の
  チェックリスト(このM2で客側フローの項目を追記する)

## すり合わせ済みの決定(2026-07-16)

1. **予約ポリシーの初期値**: 枠30分刻み / 30日先まで / 開始60分前締切
   (DB値なので管理画面(M4)で変更可能)
2. **「どちらでも」の担当割当**: 空いている中で `display_order` が小さい方
   (実質オーナー優先)
3. **可変価格メニュー**(「¥11,000〜」「約180分〜」「所要時間 —」): M2は
   固定価格・固定時間のみ。表現の拡張はメニュー管理(M4)で検討
4. **定休日・祝日ルール**(第◯曜日定休・祝日自動休業・指定日休業): M4で
   設定画面と同時に実装。M2の空き枠計算は休業日判定を入力として受ける設計に
   とどめる
5. **メニューカテゴリの実体化**: M2で `menu_categories` テーブルを追加し、
   客側のカテゴリ説明文表示に対応する
