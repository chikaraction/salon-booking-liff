# 障害時に予約を見るための控え(未着手の案、2026-11-16)

Cloudflare か Supabase が止まると、管理画面が開けず、店は「今日だれが来るか」が分からなくなる
(README の「障害時の運用」)。そのときに見られる予約の控えを、どう用意するかの案をまとめる。
**まだ実装しないと決めた。** やるときは、この文書から始める。

## 前提

- **控えは Cloudflare と Supabase の外に置く**: 管理画面にエクスポートのボタンを足しても、
  障害中はその管理画面が開けないので役に立たない
- **IT に詳しくないオーナーが扱える形にする**: ファイルを開く、探す、変換するといった手間を残さない。
  オーナーが普段使っていて、障害中も見られる場所は LINE と紙(または端末に残った画面)

## 案 1: 前日にオーナーの LINE へ予約一覧を届ける(採用したい)

前日リマインドの Cron(毎時)の送信時刻(店舗設定。既定 18:00)に、オーナーにも 1 通送る。

```
【明日 11/17(火)のご予約】3件
10:00-11:30 山田様 カット+カラー(田中)
13:00-14:00 鈴木様 カット(佐藤)
15:30-16:30 高橋様 パーマ(田中)

【明後日 11/18(水)】定休日
```

- オーナーの操作はない。いつもの LINE に届き、障害中もトークを遡れば見られる。
  スマホでもタブレットでも、そのまま一覧として読める
- 明日と明後日の 2 日分を載せる。翌日に障害が長引いても、その日の分は前日の通知に残っている
- 送れなかったときは、リマインドと同じく 21 時台まで毎時送り直す
- 一覧は送った時点のもの。送信より後に入った予約は載らないので、通知文にそう書く
  (例: 「18:00 時点の予約です」)

### 決めること・変えること

- **ADR-002 の改訂が要る**: いまは「プッシュは前日リマインドだけ」と決めている。オーナーへの通知で
  月に約 30 通増え、リマインドの約 100 通と合わせて約 130 通になる。無料枠 200 通には収まり、
  管理画面の警告(150 通)にもかからない。ただし、予約が増えると先に警告に近づく
- **オーナーの LINE を登録する**: システムはオーナーの LINE のユーザー ID をまだ知らない。
  管理画面に「LINE で通知を受け取る」ボタンを置き、オーナーがスマホで 1 回押すと、
  LIFF で開いて自分の ID を登録する形が分かりやすい。管理画面のログインと LINE の両方を確かめてから保存する
- 送る相手はオーナーだけにするか、スタッフも選べるようにするか
- 通知に客の名前が入る。オーナー自身の LINE に送るだけなので、外に出る範囲は広がらない

### 作るもの(見込み)

- 一覧の文面を作る純粋関数(`src/lib/`、テストファースト。日付の見出し・定休日・0 件のときの文)
- 送る相手の保存先(マイグレーション。RLS と grant も同じファイルに書く)
- Cron の処理への追加(`src/server/reminders.ts` の近く。1 日 1 通の一意制約で二重に送らない)
- 管理画面の登録ボタンと、LIFF での登録画面

## 案 2: 紙に印刷しなくても、スマホやタブレットで見られる一覧

### 2-a. 端末に保存される予約一覧(PWA)

管理画面に「予約の控え」という画面を足し、ホーム画面に追加して使う。

- ふだん開いたときに、これから 7 日分の予約をその端末に保存しておく
- 障害中にホーム画面のアイコンから開くと、保存しておいた一覧を
  「11/16 18:02 時点」のように時点つきで出す。保存した画面と予約は端末の中から出すので、
  Cloudflare が止まっていても開ける(Service Worker のキャッシュ)
- オーナーの操作は、最初に 1 回ホーム画面に追加することだけ
- 内容は最後に開いた時点のもの。たまに開いていないと古くなる

実装前に確かめること(いずれも未確認):

- iPhone・iPad の Safari で、ホーム画面に追加した Web アプリが Service Worker のキャッシュと
  保存したデータを長く保つか(しばらく開かないと消されないか)
- 開いていなくても裏で定期的に取り直せるか(Periodic Background Sync は iPhone で使えない可能性が高い。
  使えないなら「たまに開く」運用になる)
- OpenNext(Cloudflare Workers)で Service Worker のファイルを配信する方法
- 端末に客の名前が残る。端末のロックが前提になる。ログアウトしたら消す

新しい仕組み(Service Worker)を入れるので、やるなら ADR を起こす。

### 2-b. 印刷用の一覧(PDF でも可)

管理画面に「今週の予約を印刷」を置き、1 週間分を A4 の表にする。PC なら PDF に保存してもよい。
ADR の変更も費用も要らないが、毎週印刷するか保存する習慣がオーナーに必要になる。
スマホで PDF を「ファイル」に保存して見ることもできるが、毎週保存し直す手間がかかるので、
スマホやタブレットで見るなら 2-a か案 1 のほうが向く。

## 向かないと判断したもの

- **CSV のエクスポート、Google スプレッドシートへの同期**: 開く・探す手間がオーナーに残る。
  同期は外部サービスの設定も増える
- **DB のバックアップ(pg_dump など)**: データが消えたときの復旧には要るが、中身を読めるのは開発者だけ。
  障害中に予約を見る目的には使えない。やるなら開発者向けの別の対策として扱う

## おすすめの順番

1. 案 1(LINE)。オーナーの手間がなく、スマホでもタブレットでも見られる。足りない日数を増やすだけなら、載せる日数を変えればよい
2. 1 週間先まで見たいなどの要望が出たら、2-a(PWA)を足す
3. PC で紙の控えがほしい店には、2-b(印刷・PDF)を足す
