# Milestone 4: 管理画面コア(認証・予約カレンダー・代行登録・店側変更/キャンセル)

- 日付: 2026-07-17
- 参照ADR: ADR-003(客の操作はサーバー経由 — 対照として店側は authenticated + RLS)/
  ADR-004(EXCLUDE制約)/ ADR-005(管理画面と認証・アクセス制御)/
  ADR-006(デザインシステム)/ ADR-007(店舗固有値をコードに書かない)

## スコープ

店側が予約運用(確認・代行登録・変更・キャンセル)を管理画面で完結できるところまで。
**設定系(スタッフ・定休日・メニュー・表示設定・ダッシュボード)は M4b に切り出す**
(2026-07-17 すり合わせ決定)。

1. **管理画面認証**: Supabase Auth メール+パスワード(ADR-005)。`/admin` 配下を
   ミドルウェア+レイアウトの二重チェックで保護。ログイン画面(モックA)・ログアウト
2. **予約カレンダー**(`/admin`、ホーム): 日表示(縦=時間軸、横=スタッフ列)/
   週表示。スマホ幅では「1日×スタッフ切替」と「予約リスト」に切替(モックH・I)。
   サイドバーにナビ+ミニ集計(今日の予約件数・今月のLINEプッシュ n/200 バー)
3. **予約詳細ダイアログ**(モックC): 客名・連絡先・日時/担当・メニュー
   (スナップショット)・料金・お客様のご要望(`reservations.note`)・
   スタッフメモ(`customers.note`、編集可)+「変更」「店側でキャンセル」
4. **代行登録**(モックD): 既存顧客の検索(名前・電話)or 新規顧客入力 →
   メニュー(複数選択)・スタッフ・日時 → 空き状況の表示 → 登録(`source = 'admin'`)
5. **店側変更**: 代行登録フォームを変更モードで再利用(初期値=既存予約)。
   確定は `admin_update_reservation` RPC(UPDATEなのでEXCLUDE制約が自己衝突なしで
   判定。23P01 → 「その枠は埋まりました」)
6. **店側キャンセル**: 確認ダイアログ → `status = 'cancelled'`。
   締切(`cancel_deadline_minutes`)は客側専用の制約なので店側には適用しない

### スコープ外

- **M4b(管理画面・設定系)へ**: スタッフ設定(勤務時間・休憩・臨時休ブロック追加UI:

  150通警告: ADR-002)/ 予約ポリシー・キャンセル締切の編集UI /
  owner・staff の権限差の実装(M4のスコープでは両ロールとも全操作可のため差が出ない)
- **可変価格・可変時間メニュー**(「¥11,000〜」「180分〜」「所要時間 —」):
  M4でも見送り。固定価格・固定時間のみ(2026-07-17決定。実店舗データ投入時に再判断)
- 来店履歴の一覧画面(過去予約はカレンダーで過去日付に移動すれば見える)
- スタッフ招待UI: Supabase Authユーザーの作成はSupabaseダッシュボードで行い、
  `staff.auth_user_id` の紐付けSQLと合わせて運用手順をREADMEに記す(2名なので十分。
  セルフサインアップは無効化されていることを検証項目に含める)
- LINE通知(M5)・デプロイ(M6)。プッシュ送信はM4では増えない(読み取りのみ)ため

## 対象画面

`docs/mockups/店側-管理画面(PC/タブレット)/` の 01〜04 と
`店側-スマホ幅/` の2枚を正とする。読み取れる実装要件:

- **A. ログイン**: 店名(`salon_settings.name`)+「管理画面ログイン」+
  メール・パスワード・ログインボタンのみの1カード
- **B. カレンダー(日)**: ヘッダーに前後ナビ+「2026年7月18日(土)」+「今日」チップ+
  日/週トグル。スタッフ列見出しは「田中(オーナー)」形式。予約ブロックは
  「9:30 佐々木様」+メニュー名(+所要分)+(高さがあれば)料金。
  休憩(`staff_working_hours.break_*` 由来)は「休憩 13:00–13:30」の淡色ブロック。
  時間軸は営業時間に合わせる
- **B-2. カレンダー(週)**: 列=曜日(日〜土)。定休日(`business_hours.is_open = false`)は
  斜線ハッチング。予約はスタッフ色分け(凡例をヘッダーに)。ブロックは開始時刻+客名
  (+入る場合はメニュー名)
- **サイドバー**: 店名「LUCE 管理」/ ナビ(M4では 予約カレンダー・代行登録のみ。
  設定系の項目はM4bで画面と同時に追加)/ 下部に「今日(週表示では今週)の予約 n件」+
  「LINEプッシュ(今月) n/200通」バー
- **C. 予約詳細**: ダイアログ。お客様/連絡先/日時・担当/メニュー(+合計金額)/
  お客様からのご要望(予約時に入力)/ スタッフメモ(店内用・スタッフが記入、編集リンク)/
  「変更」(プライマリ)+「店側でキャンセル」(アウトライン)。
  `kind = 'block'` のブロックをタップした場合は対象外(M4では詳細を出さない)
- **D. 代行登録**: お客様名は検索型(入力で `name`/`phone` 部分一致の候補を表示、
  選択で既存顧客に確定。候補になければ新規顧客として名前+電話で登録)。
  メニューは複数選択(モックは単一ドロップダウンだがデータモデルに合わせる)。
  スタッフ・日付・時間を選ぶと「この枠は空いています。◯分確保できます。」/
  「この枠は埋まっています」を表示(`availability.ts` 再利用)。メモ(任意・店内用)は
  `reservations.note` へ。最後の砦はEXCLUDE制約(23P01 → エラー表示)
- **H/I. スマホ幅**: 日表示はスタッフをセグメントで切替した1列表示。
  リスト表示は「時刻・客名・メニュー/スタッフ・(選択中は終了時刻+料金)」のカード。
  週表示はスマホ幅では提供しない(モックにないため)

## データモデルへの影響

**テーブル・列の変更なし**(スタッフメモは既存の `customers.note` を使う:
2026-07-17決定)。RPCの追加・拡張のみ:

### 1. `_insert_booking` に `p_source` を追加(既定 `'line'`)

現在 `source = 'line'` がハードコードされているため、引数化して既存呼び出しの挙動を
変えずに(デフォルト値で)代行登録から `'admin'` を渡せるようにする。
既存挙動はPGliteの特性化テストで固定してから変更する。

### 2. `admin_create_reservation`(代行登録)

`(p_customer_id uuid, p_customer_name text, p_customer_phone text,
p_staff_id uuid, p_start timestamptz, p_menu_ids uuid[], p_note text)`

- `p_customer_id` があれば既存顧客、なければ名前(必須)+電話で顧客を新規作成
  (`line_user_id = NULL`)
- `_insert_booking(..., p_source => 'admin')` を呼ぶ。23P01はそのまま伝搬

### 3. `admin_update_reservation`(店側変更)

`(p_reservation_id uuid, p_staff_id uuid, p_start timestamptz,
p_menu_ids uuid[], p_note text)`

1トランザクションで: 対象が `kind = 'booking'` かつ `status = 'confirmed'` で
あることを検証(なければ `not_found`)→ メニュー合計から `during` を再計算して
`reservations` をUPDATE → `reservation_menus` のスナップショットを差し替え。
客側の `change_reservation`(旧キャンセル+新規作成)と違い**UPDATE方式**にする:
EXCLUDE制約は更新後の値を他の行とだけ照合するため自己衝突せず、予約IDが変わらない
(将来のリマインド送信ログとの対応も切れない)。23P01時は全体ロールバック。

### 権限

いずれも `security definer` + **実行権限は authenticated のみ**(public/anon は
revoke)。客側RPC(service_roleのみ)と対照的に、店側は Supabase Auth セッション
そのものをゲートにする(ADR-005)。店側キャンセルはRPC不要 — authenticated
クライアントから `status/cancelled_at` の単文UPDATE(RLS適用)。

マイグレーションはPGlite(btree_gist + authスタブ)で事前検証。
`npx supabase db push` はユーザーに依頼する。

## 新しい純粋ロジック(`src/lib/admin-calendar.ts`、テストファースト)

- **日表示の配置計算**: 営業時間(時間軸の範囲)+予約・ブロック一覧+勤務パターン →
  スタッフ列ごとの配置済みブロック(上端%・高さ%・ラベル要素)。
  休憩は勤務パターンから擬似ブロックとして生成。EXCLUDE制約により confirmed 同士は
  重ならない前提でよい(重なり回避レイアウトは不要)
- **週表示への集約**: 週の開始(日曜)〜7日分へ日別にグルーピング+定休日判定
  (M4bで第◯曜日・祝日ルールが同じ入力に載る)
- **日付ナビゲーション**: 「2026年7月18日(土)」「2026年7月13日 〜 19日」のラベル、
  前後移動、今日判定(JST。既存 `tstzrange.ts` / `calendar.ts` を再利用)
- **代行登録の空き判定**: 既存 `availability.ts` の結果から
  「この枠は空いています。◯分確保できます。」/「この枠は埋まっています」を導出
- **予約詳細・リスト表示の整形**: メニュー結合・合計金額・時刻範囲
  (既存 `my-reservations.ts` / `booking.ts` のフォーマッタを再利用)

DOM・Supabaseクライアントのimport禁止。describe/itは日本語。

## サーバー・UI

- 依存追加: `@supabase/ssr`(cookieベースのセッション。挙動は実物で確認してから使う)
- **認証**: `src/server/admin-auth.ts`(サーバー用クライアント生成+セッション取得)。
  `middleware.ts` で `/admin` 配下を保護(未ログイン → `/admin/login`)。
  ミドルウェアだけに頼らず、保護レイアウトでもセッションを再確認する(二重チェック)
- **データ取得** `src/server/admin-data.ts`: 日/週の予約+ブロック
  (顧客・スナップショット込み)、顧客検索(名前・電話の部分一致)、スタッフ・
  メニュー一覧、ミニ集計(今日/今週の件数・今月の `push_messages` 数)。
  すべて **authenticated クライアント(RLS適用)**。service_role は使わない
- **Server Action** `src/app/admin/actions.ts`(Result型): ログイン/ログアウト、
  代行登録、変更、店側キャンセル、スタッフメモ(`customers.note`)更新
- **ルーティング**: `/admin/login` / `/admin`(カレンダー)/
  `/admin/reservations/new`(代行登録)/ `/admin/reservations/[id]/edit`(変更)
- レスポンシブはTailwindのブレークポイントで切替(md未満=スマホレイアウト)。
  テーマは現行のデザイントークン(テーマB モーヴ)をそのまま使う

## アクセス制御(ADR-005の検証必須項目)

- 未ログインで `/admin` 配下 → ログインへリダイレクト(ミドルウェア+レイアウト)
- anon キーではRLSポリシーが無いため全テーブル読み書き不可(既存方針の再確認)
- Supabase のセルフサインアップが無効であること(招待制: ADR-005)
- service_role キーをクライアントコンポーネントに渡さない(既存と同じ)

## 実施順序

機能単位で都度コミット。ロジックはテストファースト。実装(src/ 配下)は
サブエージェントに委譲し、成果物はメイン側でレビューする。

1. 設計文書(本ファイル)→ すり合わせ → コミット
2. マイグレーション: `_insert_booking` の source 引数化(特性化テスト先行)+
   `admin_create_reservation` + `admin_update_reservation`
   (PGliteで検証 → `db push` はユーザーに依頼)
3. `src/lib/admin-calendar.ts` — 配置計算・週集約・ナビラベル・空き判定メッセージ
   (テストファースト)
4. 認証: `@supabase/ssr` + ミドルウェア + ログイン画面 + 保護レイアウト
   (サイドバー枠込み)
5. カレンダー: 日表示 → 週表示 → スマホ幅(スタッフ切替・リスト)+ミニ集計
6. 予約詳細ダイアログ + 店側キャンセル + スタッフメモ編集
7. 代行登録(顧客検索・空き表示・登録)
8. 店側変更(代行登録フォームの変更モード)
9. 検証(下記)+ verify-booking チェックリスト更新 + README(スタッフ登録の運用手順)

## 検証方法

- `npm test`: 配置計算(営業時間端・休憩・スマホ切替に使う整形)・週集約
  (週境界・定休日)・ナビラベル・空き判定メッセージ・RPC入出力整形のユニットテスト。
  PGlite: `_insert_booking` 特性化 / admin RPC(23P01ロールバック・not_found)
- `npm run build` / `npm run lint`
- ブラウザスモーク(開発用の店側ユーザーで):
  - ログイン → カレンダー日/週切替 → 過去・未来へナビ → スマホ幅で切替表示
  - 代行登録: 既存顧客検索・新規顧客・空き/埋まり表示 → 登録がカレンダーに出る →
    **LIFFスタブ側の日時選択で同じ枠が埋まり表示になる**(往復確認)
  - 予約詳細 → スタッフメモ編集 → 店側キャンセル → 枠が空きに戻る
  - 変更: 同枠のままメニュー変更 / 30分ずらし(UPDATE方式の自己非衝突)/
    他予約と衝突させて「枠が埋まりました」+ 元予約が無傷で残ること
  - 未ログインで `/admin` → リダイレクト。ログアウト後も同様
- verify-booking に追記して確認: anonキーでのデータアクセス拒否・セルフサインアップ
  無効・管理画面レスポンシブ実機・代行登録とLIFF予約の同時競合(23P01)

## すり合わせ済みの決定(2026-07-17)

1. **スコープ**: M4は予約運用のコア(認証・カレンダー・詳細・代行登録・店側変更/
   キャンセル)のみ。設定系(スタッフ・定休日・メニュー・表示設定・ダッシュボード)は
   M4bへ切り出す
2. **可変価格・可変時間メニュー**: M4でも見送り(固定値のみ)。実店舗データ投入時に
   再判断
3. **表示設定(M4bで実装)**: プリセット3案+フォント切替のみDB駆動にする。
   カスタム色の濃淡自動生成は将来対応(UIはグレーアウト)
4. **スタッフメモ**: 顧客単位で `customers.note` に保存(スキーマ変更なし)。
   アレルギー・次回提案は客に紐づく情報のため、次回の予約詳細にも自動で表示される
