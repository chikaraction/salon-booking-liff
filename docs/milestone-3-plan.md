# Milestone 3: マイ予約(客自身のキャンセル・変更)

- 日付: 2026-07-17
- 参照ADR: ADR-002(キャンセル確認はプッシュ不使用)/ ADR-003(マイ予約から客自身が
  キャンセル・変更)/ ADR-004(EXCLUDE制約)/ ADR-006(デザインシステム)/
  ADR-007(締切などの運用値はコードに書かずDBへ)

## スコープ

客がLIFFの「マイ予約」から自分の予約を確認・キャンセル・変更できるところまで。

1. **マイ予約一覧**(`/my`): 今後の確定予約のみ表示。リッチメニューから直接開く想定
2. **キャンセル**: 確認ダイアログ → `status = 'cancelled'`。枠は即座に空きへ戻る
   (EXCLUDE制約は `confirmed` のみ判定対象: ADR-004)
3. **変更**: 予約ウィザード(M2)を再利用し、メニュー・スタッフ・日時をすべて
   選び直せる。確定時に「旧予約キャンセル + 新規作成」を1つのRPCでアトミックに行う
4. **キャンセル締切のDB化**: `salon_settings.cancel_deadline_minutes` を追加(ADR-007)

### スコープ外

- 過去の来店履歴・キャンセル済み予約の表示(来店履歴はオーナーが管理画面で見る
  用途なのでM4以降)
- キャンセル・変更の店側への通知(M5。ADR-002: 客自身の操作時は画面表示で完結し、
  プッシュを使わない。店側は管理画面カレンダー(M4)で最新状態を見る)
- 管理画面からの変更・店側キャンセル(M4)
- LIFF実機・リッチメニュー設定(M6のデプロイ後に verify-booking で確認)

## 対象画面

`docs/mockups/客側-LIFF(スマホ縦)/07-マイ予約` を正とする。読み取れる実装要件:

- 見出し「マイ予約」+サブタイトル「今後のご予約」
- 予約カード: 「確定」バッジ / 右上に残り日数 / 「7月18日(土)11:00〜」/
  「カット+カラー / 田中」(メニュー名を「+」で結合し「/ スタッフ名」)/
  「¥11,550 ・ 約150分」(スナップショットの合計)/ 下部に「変更」「キャンセル」ボタン
- 右上の残り日数はモックで「あと3日」と「8月2日」が混在 →
  **7日以内は「あと◯日」(当日は「本日」)、8日以上先は「◯月◯日」** と定義する
- キャンセル確認はボトムシート: 「予約をキャンセルしますか?」+ 対象予約の要約
  (日時・メニュー/スタッフ)+ プライマリの「キャンセルする」+「戻る」
- モックにない状態の扱い:
  - 予約が0件 → 「今後のご予約はありません」+ 予約フローへの導線
  - 締切超過 → 「変更」「キャンセル」を無効化し「変更・キャンセルはお店に直接
    ご連絡ください」を表示

## データモデルへの影響

スキーマ本体は変更しない。追加のみ:

### 1. キャンセル締切列(`salon_settings`)

| 列                        | 型      | default | 意味                                       |
| ------------------------- | ------- | ------- | ------------------------------------------ |
| `cancel_deadline_minutes` | integer | 60      | 開始何分前まで客自身でキャンセル・変更可か |

店舗固有の運用値なのでDBへ(ADR-007)。管理画面での編集はM4。初期値は
直前締切(`min_lead_minutes`)と同じ60分。

### 2. キャンセルRPC(`cancel_reservation`)

`(p_line_user_id, p_reservation_id)`。RPC内で以下をすべて検証し、
`status = 'cancelled'`, `cancelled_at = now()` に更新する:

- 予約が存在し、`kind = 'booking'` かつ `status = 'confirmed'` であること
- **本人の予約であること**(`customers.line_user_id` で照合。他人の予約IDを
  渡されても `not_found` 相当で拒否)
- 締切前であること(`now() < 開始時刻 − cancel_deadline_minutes`)。
  アプリ側の締切判定は表示用の補助とし、最終判定はRPC内で行う(ADR-004と同じ発想)

### 3. 変更RPC(`change_reservation`)

`(p_line_user_id, p_reservation_id, p_staff_id, p_start, p_menu_ids, p_note)`。
1トランザクションで:

1. 旧予約を `cancel_reservation` と同じ条件で検証してキャンセル
2. `create_reservation` と同じ手順で新予約+メニュースナップショットをINSERT

旧を先にキャンセルするため、同じスタッフの近接時間へずらす変更でも自己衝突しない。
新予約がEXCLUDE制約に違反した場合は23P01がそのまま伝搬し、
**トランザクション全体がロールバックされて旧予約は無傷で残る**(最重要の性質)。
`create_reservation` との重複ロジックは内部関数に括り出して共有する。

いずれも `security definer` + service_role のみ実行可(ADR-003: 客の操作はサーバー経由)。
マイグレーションはPGlite(btree_gist + authスタブ)で事前検証 → `npx supabase db push`。

## 空き枠計算への影響

変更フローの日時選択では、自分の旧予約が「埋まり」として見えてしまうと
「同じ枠のままメニューだけ変える」「30分だけずらす」ができない。
`src/lib/availability.ts` の純粋関数は既存予約リストを入力に取るため**変更不要**で、
`src/server/booking-data.ts` の予約取得に「除外する予約ID」を渡してサーバー側で
除くだけでよい(念のため既存挙動は現行テストで固定済みであることを確認する)。

## 新しい純粋ロジック(`src/lib/my-reservations.ts`、テストファースト)

- 残り日数ラベル: `now` と開始時刻(JST暦日差)から「本日 / あと◯日(1〜7日)/
  ◯月◯日(8日以上)」を返す
- キャンセル・変更可否: `(now, 開始時刻, cancel_deadline_minutes)` → 可否
- カード表示整形: `reservation_menus` スナップショットからメニュー名の結合・
  合計金額・合計所要時間、日時表示(既存の `booking.ts` / `utils.ts` の
  フォーマッタを再利用)

DOM・Supabaseクライアントのimport禁止。describe/itは日本語。

## サーバー・UI

- `src/server/booking-data.ts` に「line_user_id の今後の確定予約一覧
  (メニュースナップショット+スタッフ名込み、開始時刻昇順)」の取得を追加
- Server Action(`src/app/my/actions.ts`、Result型で返す):
  - `getMyReservations(idToken)` — 検証 → 一覧
  - `cancelReservation(idToken, reservationId)` — 検証 → RPC。
    reason: `auth | not_found | deadline_passed | server_error`
- 変更の確定: 予約ウィザードに「変更モード」(変更元の予約ID+初期選択値)を追加。
  確定時は `submitReservation` に変更元IDがあれば `change_reservation` RPC を呼ぶ
  (23P01 → 「その枠は埋まりました」で日時選択へ戻すのはM2と同じ)
- 予約完了画面(M2)に「マイ予約で確認できます」の導線を追加(mockup-brief 5)
- LIFFスタブ(`NEXT_PUBLIC_LIFF_STUB=1`)でマイ予約もブラウザ確認できること

## 実施順序

機能単位で都度コミット。ロジックはテストファースト。

1. 設計文書(本ファイル)→ すり合わせ → コミット
2. マイグレーション: `cancel_deadline_minutes` + `cancel_reservation` +
   `change_reservation`(PGliteで検証 → `db push`)
3. `src/lib/my-reservations.ts` — 残り日数・可否判定・表示整形(テストファースト)
4. サーバー: 予約一覧取得(+空き枠の自予約除外)+ Server Action
5. UI: マイ予約一覧 + キャンセル確認ダイアログ + 空状態
6. UI: 変更フロー(ウィザードの変更モード + 完了画面の導線)
7. 検証(下記)+ verify-booking チェックリスト更新

## 検証方法

- `npm test`: 残り日数ラベル(当日・7日/8日境界)・締切可否(ちょうど締切時刻)・
  表示整形のユニットテスト
- `npm run build` / `npm run lint`
- ブラウザスモーク(LIFFスタブ):
  - 予約作成 → マイ予約に表示 → キャンセル → 一覧から消え、同じ枠が空きに戻る
  - 変更: 同じ枠のままメニュー変更 / 同じスタッフで30分ずらし(自予約除外の確認)
  - 締切超過の予約(設定値を一時的に大きくして再現)でボタンが無効化される
  - 他人の予約IDでキャンセルを試み拒否される(Server Actionを直接叩く)
- verify-booking に追記して確認: 変更確定と他客の新規予約が同枠で競合したとき
  旧予約が無傷で残ること(ロールバック)、LIFF実機のマイ予約導線(M6後)

## すり合わせ済みの決定(2026-07-17)

1. **変更の範囲**: メニュー・スタッフ・日時すべて変更可。ウィザードを再利用し、
   「旧キャンセル+新規作成」をRPCでアトミックに行う
2. **キャンセル締切**: `salon_settings.cancel_deadline_minutes`(初期値60分)を
   追加。締切後は「お店に直接ご連絡ください」表示。管理画面での編集はM4
3. **表示範囲**: モック07準拠で「今後の確定予約のみ」。過去履歴・キャンセル済みは
   表示しない
