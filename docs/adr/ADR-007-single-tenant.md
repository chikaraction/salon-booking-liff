# ADR-007: マルチテナント化はせず、2店舗目はインスタンス複製で対応

- ステータス: 承認済み
- 日付: 2026-07-15

## Context(状況)

システムはオーナーの美容室1店舗のために作るが、オーナーの家族が美容の店を営んでおり、将来このシステムを使いたくなる可能性がある。
「複数店舗対応」と聞くとマルチテナント設計(1つのDB・1つのデプロイで複数店舗を扱う)を検討したくなるが、その要否を判断する必要がある。

## Decision(決定)

- **マルチテナント化はしない。** テーブルに店舗IDは持たせず、1デプロイ=1店舗の前提で作る
- 2店舗目が必要になったら、**同じコードを別インスタンスとしてもう1セットデプロイ**する
  - 複製単位: Supabaseプロジェクト / Cloudflareデプロイ / LINE公式アカウント+LIFF を店舗ごとに1セット
  - コードは1リポジトリを共有(改善は両店舗に還元される)
- そのために守る設計原則:
  1. **店舗固有の情報をコードに書かない。** 店名・メニュー・カテゴリ・料金・所要時間・営業時間・スタッフはすべてDBのデータとし、管理画面から設定できるようにする
  2. メニューカテゴリは自由入力(美容室の「カット/カラー」もマッサージ店の「もみほぐし/オイル」も同じ仕組みで表現できる)
  3. 環境ごとに変わる値(Supabase接続情報、LINEチャネルID等)は環境変数に置く

## 理由

- マルチテナント化は全テーブルへの店舗ID付与、店舗横断のアクセス制御(RLS)、店舗ごとの管理者権限分離など、開発・テストコストが大幅に増える。想定は2店舗であり、コストに見合わない
- インスタンス複製なら、Supabase・Cloudflareの無料枠がプロジェクト単位で付くため、2店舗になっても運用コストはほぼ0円のまま
- 店舗間でデータが物理的に分離されるため、権限バグで他店のデータが見える事故が構造的に起こらない
- 「設定で店の違いを吸収する」原則は1店舗運用でも価値がある(メニュー変更のたびにコード修正が不要)

## 検討した代替案

- **マルチテナント設計**: 数十店舗に提供するSaaSなら正解だが、2店舗では過剰。→ 却下(将来本当にSaaS化するなら、その時点で新ADRとして再設計を検討)
- **2店舗目はコードをフォークして別リポジトリ**: 改善が分岐して二重メンテになる。→ 却下(リポジトリは1つを共有)

## Consequences(影響)

- 良い点: 設計・実装がシンプルなまま。2店舗目の追加は「デプロイ作業」であって「開発作業」ではなくなる
- 注意点: 2店舗目のデプロイ手順(Supabase作成→マイグレーション→LINE設定→環境変数→デプロイ)を docs/setup.md に文書化しておくこと。店舗を横断した集計(2店舗合計の売上など)は標準では見られない — 必要になったら別途検討
- リポジトリ名は店名に依存しない汎用名(例: `salon-booking-liff`)とする
