# ADR-004: ダブルブッキング防止(DBレベルの排他制約)

- ステータス: 承認済み
- 日付: 2026-07-14

## Context(状況)

スタッフ指名制のため「同じスタッフ・同じ時間帯」に2件の予約が入ることは絶対に防がなければならない。小規模でも、空き枠表示を見た2人がほぼ同時に予約ボタンを押す競合は現実に起こる。アプリ側のチェック(「空きを確認してから保存」)だけでは、確認と保存の間に他の予約が入るレースコンディションを防げない。

## Decision(決定)

- ダブルブッキング防止は**PostgreSQLの制約で保証**する(アプリ側チェックは補助)
- 予約テーブルに時間範囲型(`tstzrange`)を持たせ、**EXCLUDE制約**で「同一スタッフの時間範囲の重複」をDBが拒否する構成にする

```sql
-- 概念図(実装時に精緻化)
CREATE EXTENSION IF NOT EXISTS btree_gist;

CREATE TABLE reservations (
  id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  staff_id uuid NOT NULL REFERENCES staff(id),
  during tstzrange NOT NULL,          -- 予約の時間範囲
  status text NOT NULL DEFAULT 'confirmed',
  EXCLUDE USING gist (
    staff_id WITH =,
    during WITH &&
  ) WHERE (status = 'confirmed')      -- キャンセル済みは重複判定から除外
);
```

- 挿入が制約違反になった場合、アプリは「その枠は埋まりました」と表示して枠選択に戻す

## 理由

- DB制約は同時リクエストが何件来ても整合性を保証する唯一の確実な手段。アプリのロジックにバグがあっても最後の砦になる。
- Supabase(PostgreSQL)を選んだこと(ADR-001)でEXCLUDE制約がそのまま使える。
- 施術時間がメニューによって異なる(30分カット、120分カラー等)場合も、固定枠方式と違い時間範囲の重複判定で自然に対応できる。

## 検討した代替案

- **アプリ側で空き確認してから保存**: レースコンディションを防げない。→ 単独では不十分(UX向上のための事前チェックとしては併用)
- **固定30分枠+UNIQUE制約(staff_id, slot)**: シンプルだが施術時間が枠をまたぐメニューの表現が複雑になる。→ 却下
- **悲観ロック(SELECT FOR UPDATE)**: 実装は可能だがロック範囲の設計を誤ると防げない。宣言的なEXCLUDE制約のほうがAI主導開発でも間違いにくい。→ 却下

## Consequences(影響)

- 良い点: 同時アクセスでもダブルブッキングが構造的に発生しない。メニューごとの施術時間の違いにも対応。
- 注意点: `btree_gist`拡張が必要(Supabaseで利用可能)。「キャンセル済み予約は重複OK」等の条件をWHERE句で正しく設計する必要がある。営業時間外・休憩時間のブロックも同じ仕組み(スタッフの「予約不可時間」を同テーブルまたは同制約で管理)で実現する。
