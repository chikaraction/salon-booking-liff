# ADR-005: 店側管理画面と認証

- ステータス: 承認済み
- 日付: 2026-07-14

## Context(状況)

店側はWeb管理画面で予約を管理したい。1店舗・スタッフ数名の小規模運用。顧客はゲスト予約(ADR-003)でアカウントを持たないため、認証が必要なのは店側スタッフのみ。

## Decision(決定)

- 管理画面は同じNext.jsアプリ内の `/admin` 配下に実装(別アプリにしない)
- **レスポンシブ対応必須**: 基本はPC/タブレットだが、外出先のスマホからも予約確認・簡単な操作ができること(スマホ幅ではカレンダーを1スタッフ切替またはリスト表示に切替)
- 店側の認証は **Supabase Auth のメール+パスワード**(スタッフを招待制で登録)
- 権限は当面 **「オーナー」「スタッフ」の2種類**のみ
  - オーナー: スタッフ管理・営業時間/メニュー設定・全予約の操作
  - スタッフ: 予約の閲覧・代行登録・代行キャンセル
- 管理画面の必須機能(MVP):
  1. 予約カレンダー(日/週表示、スタッフ別)
  2. 電話予約の代行登録・代行変更・代行キャンセル(LINEを使わない客の受け皿: ADR-003。客からの電話での変更依頼にも対応)
  3. スタッフごとの勤務時間・予約不可時間の設定
  4. メニュー(施術内容・所要時間)の管理

## 理由

- 1店舗規模で管理画面を別システムにする複雑さは不要。同一アプリならデータモデル・デプロイが一本化できる。
- Supabase Auth(ADR-001)をそのまま使えば認証の実装コストがほぼゼロ。
- 電話予約は小規模サロンでは必ず発生するため、代行登録は初期リリースに必須。これがないと「電話予約はシステム外」になり空き枠管理が破綻する。

## 検討した代替案

- **Googleカレンダー連携で管理**: 手軽だが、ダブルブッキング防止(ADR-004)の制約をDB外のカレンダーに保証させられない。双方向同期は複雑でAI主導開発のリスクが高い。→ 却下(将来「閲覧用の一方向同期」なら検討可)
- **Supabaseのダッシュボードを直接使う**: 無料だが非エンジニアの店側スタッフには操作が危険(データ直編集)。→ 却下
- **細かいロール設計(受付/施術者/マネージャー等)**: 数名規模では過剰。→ 2ロールに簡素化

## Consequences(影響)

- 良い点: 追加コストなしで店側運用が完結。電話予約もシステムに集約され、空き枠の正が一つになる。
- 注意点: `/admin` 配下のアクセス制御(ミドルウェア+SupabaseのRow Level Security)を確実に実装する必要がある。実装時のセキュリティレビュー項目として明記する。
