# マイルストーン実装ワークフロー

tendledgeプロジェクトで確立した進め方をsalon-booking用に翻案したもの。
この型に沿うことで、テストの抜け・コミットのまとめすぎ・ADRとの乖離を防ぐ。

## 手順

1. **ADRとの整合を確認する** — 着手前に `docs/adr/` の関連ADRを読む。ADRと
   矛盾する実装が必要になったら、実装せず先にユーザーと相談し、必要なら
   新ADRを起案してから進める。
2. **設計文書を書く** — `docs/milestone-N-plan.md`。スコープ / 対象画面
   (docs/mockups/ の該当スクショ) / データモデルへの影響 / 実施順序 / 検証方法。
   ユーザーと擦り合わせてから実装に入る。
3. **タスク分解** — TaskCreate で機能単位に登録し、依存関係(blockedBy)を張る。
   着手時に in_progress、完了時に completed へ更新する。
4. **ロジックにテストファースト** — 予約枠計算・営業時間判定・通知文生成などの
   判断ロジックは `src/lib/` に純粋関数として置き、まず `*.test.ts` に日本語の
   describe/it で仕様を書いてから実装する(DOM / Supabaseクライアントのimport禁止)。
   既存コードを変更する場合は先に特性化テストで現在の挙動を固定する。
5. **UI・DBアクセスは薄く** — コンポーネントとServer Actionは配線に徹する。
   判断ロジックが現れたら `src/lib/` に押し戻す。ダブルブッキング防止は
   アプリ側チェックに頼らず、必ずDB制約(ADR-004)を最後の砦にする。
6. **検証** — `npm test` と `npm run build` を通し、ブラウザで対象画面を
   スモークテストする。DB制約・LIFF・LINE通知などローカルで完結しない項目は
   `verify-booking` スキルのチェックリストをユーザーに提示する。
7. **機能単位で都度コミット** — 1機能が完成しテストが通った時点でコミットする
   (確認不要・メッセージは日本語)。後からの分割は高コストなのでやらない。
8. **マージ後の後片付け** — PRのマージを確認したら(`gh pr view --json state,mergedAt`)、
   `git fetch --prune` → メインブランチを fast-forward → **そのマイルストーンの
   ブランチだけ** `git branch -d` する(無関係な過去ブランチは触らない)。
   セッションもマイルストーン単位で区切る(決定はADR・設計文書・コミットに残る)。

## 分担の指針(トークン効率)

- 設計・スキーマ変更・横断的リファクタ・レビューはメインセッションが担当。
- 独立性が高く仕様が明確な機能(例: メニュー管理画面)はサブエージェントに
  委譲してよい。ただし成果物は必ずメイン側でレビューする。委譲時はこの
  スキルの手順 4〜7 を指示に含めること。

## このリポジトリ固有の注意

- スキーマ変更は必ずマイグレーションファイルとして残す(Supabaseダッシュボードでの
  直接変更は禁止)。EXCLUDE制約(ADR-004)を壊す変更は特に慎重に。
- **public にテーブルを作るときは、同じマイグレーションで grant を書く。**
  Supabaseは2026-10-30以降、新しいテーブルにData APIの権限を自動では付けない
  (書き忘れるとアプリから「permission denied」になる)。形は既存テーブルに合わせる
  (`supabase/migrations/20261021000000_explicit_table_grants.sql`):
  `grant select, insert, update, delete on table public.<テーブル> to authenticated, service_role;`
  anon には付けない(客側は service_role、管理画面は authenticated で読む)。誰が何を
  できるかはRLSポリシーで決めるので、RLSの有効化とポリシーも同じマイグレーションに書く。
  PGliteで検証するときは alter default privileges をしないこと(自動grantがある前提だと
  書き忘れを見逃す)。
- 管理画面(/admin)を触るときはアクセス制御(ミドルウェア+RLS)の確認を検証項目に含める。
- LINEプッシュ送信を増やす変更は、無料枠200通/月の消費見積もりをADR-002と照合する。
- 店舗固有の値(店名・メニュー・営業時間)をコードに書かない(ADR-007)。
