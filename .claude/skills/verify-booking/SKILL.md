# 予約システム実機確認チェックリスト

ユニットテストとビルドが通っても、以下はデプロイ環境・LINE実機・複数端末で
のみ確認できる。tendledgeのverify-tauriスキルと同じ運用: **機能を追加したら
対応するチェック項目をここに追記する**。

## 画面のURL一覧

確認の入口。開発サーバーは `npm run dev`(既定で http://localhost:3000)。
見た目の正は `docs/mockups/` のスクリーンショット。

### 店側(管理画面)

| URL | 画面 | 備考 |
| --- | --- | --- |
| `/admin/login` | ログイン | 招待制。この画面からアカウントは作れない(ADR-005) |
| `/admin` | 予約カレンダー | ログイン後の着地点。日表示・週表示 |
| `/admin/reservations/new` | 代行登録(ページ版) | カレンダーからはダイアログで開く。直URLだとページ版 |
| `/admin/reservations/[id]/edit` | 予約の編集(ページ版) | 同上。`[id]` は reservations.id |
| `/admin/dashboard` | ダッシュボード | オーナー・スタッフとも閲覧可。モックG |
| `/admin/settings/business` | 営業日・営業時間 | オーナーのみ。モックE-2 |
| `/admin/settings/staff` | スタッフ | オーナーのみ。モックE |
| `/admin/settings/menus` | メニュー | オーナーのみ。モックF |
| `/admin/settings/salon` | 店舗・予約設定 | オーナーのみ |
| `/admin/settings/display` | 表示設定 | オーナーのみ。モックF-2 |

`/admin` 配下はすべてログインが必要(`src/middleware.ts` の matcher が `/admin/:path*`)。
設定の5画面はサイドバーの「設定」グループから開けるが、スタッフロールでは
リンクが出ず、直URLでも弾かれる。`/admin/settings` 自体のページは無い(404)。

### 客側(LIFF)

| URL | 画面 | 備考 |
| --- | --- | --- |
| `/booking` | 予約フロー | メニュー → スタッフ → 日時 → お客様情報 → 確認 → 完了 |
| `/my` | マイ予約 | 予約の変更・キャンセル |

LINEを通さずブラウザで開くには `NEXT_PUBLIC_LIFF_STUB=1`(LINEログインの代わりに
`stub:<userId>` のダミートークンを使う。本番では必ず拒否される)。

| `/` | LIFFの入口(M6) | LIFFのエンドポイントURL。`liff.init()` で `liff.state` の行き先(`/my` など)へ、無ければ `/booking` へ。スタブ時は常に `/booking` |

本番(M6〜)は `https://<Worker名>.<サブドメイン>.workers.dev`。LINEからは
`https://liff.line.me/<LIFF ID>/booking`・`/my`(リッチメニューのリンク)で開く。

## ダブルブッキング防止(ADR-004)

- [ ] 2つのブラウザで同じスタッフ・同じ時間帯の予約画面を開き、ほぼ同時に
      確定 → 片方だけ成功し、もう片方に「その枠は埋まりました」が表示される
- [ ] キャンセル済み予約と同じ枠に新規予約できる(WHERE status='confirmed' の確認)
- [ ] 所要時間の長いメニュー(例: 180分)が、途中の時間帯の別予約と重複できない
- [ ] スタッフの休憩・予約不可時間に重なる枠が客側に表示されない

## 客側予約フロー(M2)

- [ ] 日時選択で、埋まっている時刻が取り消し線+グレーで表示され押せない。
      勤務時間・所要時間の関係で確保できない時刻はそもそも表示されない
- [ ] 直前締切(開始60分前)を過ぎた当日の枠、受付期間(30日先)を超える日付が
      選択できない(いずれも salon_settings の値。変更したら反映されること)
- [ ] 「どちらでも」で予約 → 空いているスタッフのうち表示順が小さい方
      (実質オーナー)に割り当てられる。オーナーが埋まっている枠では
      もう一方に割り当てられる
- [ ] 初回予約で customers に1行だけ作成され、ご要望欄が reservations.note に、
      メニューのスナップショット(名前・料金・所要時間)が reservation_menus に入る
- [ ] メニュー選択でカテゴリ見出しに説明文(menu_categories.description)が表示される
- [ ] 完了画面の「確認のメッセージをLINEにお送りしました」は、LINEに定型文を送れたときだけ出る
      (M5。スタブ・外部ブラウザでは出ない。下の「通知」節)

## マイ予約・キャンセル・変更(M3)

- [ ] **変更の競合ロールバック**: 客Aが変更の確認画面まで進んだ状態で、別ブラウザの
      客Bが変更先と同じ枠を先に予約 → 客Aの変更確定は「その枠は埋まりました」になり、
      **客Aの元の予約が confirmed のまま無傷で残っている**(DBで status を確認)
- [ ] キャンセル直後に同じ枠が別客の日時選択に「空き」として出る
- [ ] 変更で「同じ枠のままメニューだけ追加」「同じスタッフで30分ずらし」ができる
      (自分の旧予約の枠が「埋まり」表示にならない)
- [ ] 締切(開始 cancel_deadline_minutes 前)を過ぎた予約は変更・キャンセルボタンが
      無効化され「お店に直接ご連絡ください」が表示される。salon_settings の値を
      変えると反映される
- [ ] Server Action を直接叩いて他人の予約IDのキャンセル・変更を試みる → 拒否され、
      対象予約に変化がない(RPC内の本人確認)
- [ ] LINE実機: リッチメニューの「マイ予約」ボタンから /my が直接開く(M6デプロイ後)

### ビルド・設定

- [ ] Workers Builds のビルドログでデプロイ前チェックが通り、警告
      (`NEXT_PUBLIC_LIFF_ID` 未設定など)が想定どおり。OpenNext の
      「Node.js middleware support is experimental」警告が**出ていない**
      (ミドルウェアは Edge の `src/middleware.ts`)
- [ ] `NEXT_PUBLIC_LIFF_STUB` を Build variables に入れると、ビルドがデプロイ前チェックで止まる
      (確認したら変数を消して再ビルド)
- [ ] 本番のクライアントJS(DevTools の Sources / `_next/static/chunks`)に
      service_role キーの値が含まれない
- [ ] 本番のクライアントJSに **LIFF ID が文字列で埋め込まれている**。Build variables に
      入れる前のビルドや、変数を足しただけ(再ビルドなし)の版では
      `env.NEXT_PUBLIC_LIFF_ID` を読む形のまま残り、LINE で開いても本人確認できない。
      LIFF ID を入れたら必ずビルドを**再試行**する(2026-10-21 の初回デプロイで実際に起きた)
- 注: `stub:U-dev-user-1` の文字列自体はクライアントJSに残る(`src/liff/client.ts` の定数)。
  本番では `NEXT_PUBLIC_LIFF_STUB` が未設定でスタブ分岐に入らず、サーバーも本番では
  スタブを必ず拒否するので問題ない

### 客側(LINE実機。テスト用公式アカウント)

- [ ] リッチメニュー「予約する」→ `/booking` が開き、ログイン操作なしで本人が特定される
- [ ] リッチメニュー「マイ予約」→ **`/my` が直接開く**(`/` の入口から `liff.state` で振り分け。

- [ ] LINE内ブラウザでテーマカラー・フォントが表示設定どおり(Noto Sans JP は初回に
      一瞬フォールバックが出ることがある)。表示設定を変えると**再ビルドなしで**反映される
- [ ] LINE内ブラウザ(スマホ縦)で客側の全画面が崩れない
- [ ] **画面下のボタン**(予約画面の「次へ」等・キャンセル確認シート)が、端末の角の丸み・
      ホームバーと重ならず、画面下端との間に余白がある(iPhone は `viewport-fit=cover` +
      `env(safe-area-inset-bottom)`。2026-10-21 の実機確認での指摘で対応)
- [ ] 本番に `stub:U-test` のIDトークンで Server Action を送ると認証エラーになる

- [ ] LINE以外のブラウザで本番の `/booking` を開いたときの表示が想定どおり

### 管理画面

- [ ] 未ログインで本番の `/admin` 配下 → `/admin/login`。ログイン後は各画面が開く
- [ ] ログインして**1時間以上たってから**操作しても使い続けられる

## 通知(ADR-002・M5)

前提: README「初回デプロイの手順」3 の設定(Messaging API・Webhook・応答設定・3つの Secret)と、
マイグレーション `20261022000000_m5_notifications.sql` の適用が済んでいること。
まずテスト用公式アカウントで確認し、本番切り替え後に店のアカウントで予約確認だけもう一度見る。

### 予約確認(応答メッセージ・無料)

- [ ] リッチメニューから予約 → トークに客の発言「予約を確定しました」と、公式アカウントからの
      予約内容(日時・メニュー・担当・合計・マイ予約のURL・店名)が並ぶ。完了画面に
      「確認のメッセージをLINEにお送りしました」が出る
      (リッチメニューから開いた LIFF で `liff.sendMessages` が使えることは 2026-10-22 に
      テスト用公式アカウントで確認済み。URL の下に出る「予約システム」のカードは LINE が
      付けるリンクのプレビューで、サイトのタイトル・説明文)
- [ ] 初回は `chat_message.write` の同意画面が出る(出なければ LIFF のスコープを確認)。
      画面では「トークルームへのメッセージ送信」のトグルとして出る(2026-10-23 確認)。
      出し直すには LINE アプリの 設定 → アカウント → 連動アプリ で LINE ログインチャネルとの
      連動を解除する(userId はプロバイダー単位なので変わらず、顧客の紐づけは保たれる)
- [ ] 同意画面で「トークルームへのメッセージ送信」を**オフ**にして予約 → 予約はでき、完了画面の
      補足文は出ず、トークにも何も出ない(2026-10-23 確認)。
      理由(LIFF API リファレンスの仕様からの説明で、実機では観察していない): スコープが
      許可されていないと `liff.sendMessages` は 403 で失敗し、`sendConfirmationMessage`
      (`src/liff/client.ts`)がログを残さず false を返す。クライアント側の処理なので Workers Logs には出ない
- [ ] マイ予約から変更 → 「予約を変更しました」と変更後の内容が返る
- [ ] キャンセル → LINE のトークには何も出ない(画面表示で完結)
- [ ] ふだんの発言(「こんにちは」・定型文の言い回し違い)には自動応答しない。OA Manager の
      チャットに届き、店から手動で返信できる
- [ ] PCの外部ブラウザで LIFF の URL(`https://liff.line.me/<LIFF ID>/booking`)を開く →
      「LINEアプリから開いてください」が出て予約に進めない(IDトークンが取れないため。
      LINE ログインは呼ばない: ADR-003)。スマホのブラウザでは LINE アプリが開くはず(推測)
- 注(既知の制約・確認しない): 公式アカウント以外の友だちとの1対1トークに貼った LIFF の URL から
  予約すると、`liff.sendMessages` は LIFF を開いたトークに送るので、定型文がその友だちとのトークに
  出て、完了画面に補足文も出てしまう(推測)。客は通常リッチメニューから開くので確認しないと
  決めた(2026-10-23)
- [ ] 予約から10分以上たってから「予約を確定しました」と手入力 → 応答しない
- [ ] トークの応答がプッシュ扱いになっていない: ダッシュボードのプッシュ送信数が増えない
- [ ] Workers Logs で Webhook の処理時間を見る(応答トークンは受信から1分以内)

### 前日リマインド(プッシュ・1予約1通)

- [ ] 管理画面の店舗設定で送信時刻をいまの時(例: 14時台なら 14:00)にし、翌日の予約を
      **送信時刻より前に**入れておく → 次の毎時0分にリマインドが1通届く
      (送信時刻の後に入れた翌日の予約には送らない仕様)
- [ ] ダッシュボード・サイドバーのプッシュ送信数が1増え、`push_messages` に
      `type = 'reminder'` で予約IDつきの行が1行入る
- [ ] 次の毎時0分に**2通目が来ない**(送信済みの記録で除外)
- [ ] 代行登録の電話客(LINEなし)の翌日予約には送られない。キャンセル済みにも送られない
- 注: 開発用スタブ(`npm run dev`)で作った顧客は `line_user_id` が `U-dev-…` で、LINE の客として
  対象に選ばれる。存在しないIDなので LINE がエラーで返し、誰にも届かず記録もされないが、
  21時台まで毎時「前日リマインドの送信に失敗しました」がログに出る。本番前にテスト用の顧客・予約を
  削除すれば出なくなる(M6 計画書の手順 E)
- [ ] Workers Logs に「前日リマインド: 完了」と集計(sent など)が出る。送信時間帯の外では
      「送信時間帯ではありません」
- [ ] **Secret を入れたら最初に**、`/api/cron/reminders` に本番URLで Bearer なしの POST → 401。
      **500 なら Worker から `CRON_SECRET` が見えていない**(入口の最初で未設定を例外にしている)。
      2026-10-22 は一覧に `CRON_SECRET` があるのに 500 で、値を入れ直したら 401 になった
      (値が空のまま保存されていたか、実行中の版に入っていなかった。中身の違う値なら 500 ではなく
      401 になるので区別できる)。このとき Cron の
      ログは「Cron(0 * * * *)の前日リマインドが失敗しました: HTTP 500」
      ```bash
      curl -s -o /dev/null -w "%{http_code}\n" -X POST https://<Worker名>.<サブドメイン>.workers.dev/api/cron/reminders
      ```
- [ ] LINE の `Get consumption`(今月の送信数)と `push_messages` の今月の件数を一度照合する
      (ブロック中の客への送信は LINE 側で数えられないので、`push_messages` の方が多いことはある)
- [ ] 確認が終わったら送信時刻を既定(18:00)か店の希望の時刻に戻す

## 管理画面コア(M4・ADR-005)

### 認証・アクセス制御

- [ ] 未ログイン状態で /admin 配下のURL(/admin・/admin/reservations/new など)を
      直接開くとログイン画面に飛ばされる。ログアウト後も同様
- [ ] 誤ったメール/パスワードで「メールアドレスまたはパスワードが違います」が出る
- [ ] **anonキーでのアクセス拒否**: anon キー(公開キー)で各テーブルを直接読み書き
      しようとすると、RLSポリシーが無いため全拒否される(SQL/REST で確認)
- [ ] **セルフサインアップ無効**: Supabase の Authentication 設定で新規サインアップが
      無効になっている(招待制: ADR-005)。/admin/login からアカウント作成できない
- [ ] service_role キーがクライアントバンドルに含まれない(NEXT_PUBLIC_ でない)
- [ ] **本番の顧客データを入れる前**: 検証用に作ったAuthユーザー(権限差の確認で
      `staff.auth_user_id` を紐付けずに作ったものなど)を Authentication → Users から
      **削除した**。紐付けが無くても予約の作成・キャンセルと顧客情報の閲覧はできる
      (`reservations` / `customers` のRLSは authenticated 全許可)ため、
      設定が触れないだけで無害なアカウントではない。
      1店舗目は開発に使っているSupabaseプロジェクトがそのまま本番になる構成
      (README「2店舗目の追加」は別プロジェクトを新規作成する手順)なので、
      開発用に作ったものが本番に残りうることに注意する

### 予約カレンダー

- [ ] 日表示: 縦=時間軸・横=スタッフ列。予約ブロック・休憩・予約不可(斜線)が
      正しい位置に出る。前後ナビ・「今日」・日/週トグルが効く
- [ ] 週表示: 曜日列、定休日が斜線ハッチング、スタッフ色分けの凡例が出る
- [ ] **日付ジャンプ**: ヘッダーの日付ピッカーで1か月先など任意の日付へ一度で移動
      できる(日表示・週表示とも)。日付を消して空欄にしても勝手に遷移しない
- [ ] **定休日の視認性**: 週表示の定休日が一目で分かる(斜線+淡い下地+定休日バッジ)。
      定休日に予約がある場合も予約ブロックが前面で読める。ダークテーマでも破綻しない
- [ ] **週表示の重なり**: 別スタッフの予約を同じ日の同じ時間帯に入れると、
      週表示で左右に並んで**両方見える**(片方が隠れない)。3人分重ねると3等分になり、
      時間が接しているだけ(前の終了 == 次の開始)の2件は横幅いっぱいのまま。
      隣り合うカードの境目が輪郭で分かる
- [ ] **週表示のツールチップ**: 幅が狭くて文字が切れているカードにカーソルを乗せると、
      「11:00 山田様 / カット + カラー / 田中」が出る。カードのクリックは
      従来どおり予約詳細ダイアログが開く
- [ ] スマホ幅: 「タイムライン(1スタッフ切替)」と「リスト」に切り替わり、
      横スクロールが発生しない(レスポンシブ節とも重複)
- [ ] サイドバーのミニ集計(今日の予約件数・今月のLINEプッシュ n/200 バー)が
      実データと一致する

- [ ] **代行登録のメニュー順**: 代行登録・予約の編集・カレンダーの予約ダイアログの
      メニュー一覧が、メニュー管理画面と同じ順(カテゴリ順 → カテゴリ内の表示順)に
      並ぶ。メニュー管理で並べ替えたり、1件だけ編集したりしても、その順が保たれる

### 空き枠クリック → 代行登録ダイアログ

- [ ] **空き枠クリック(日表示)**: 日表示でスタッフ列の空いている時間帯をクリックすると、
      その場で代行登録ダイアログが開き、スタッフ・日付・時刻が初期入力済みになる。
      時刻は `salon_settings.slot_interval_minutes` の刻みに切り下がる
      (刻みを15分に変えると15分単位で入る = ハードコードしていない)
- [ ] **既存導線の非回帰**: 予約カードをクリックしたときは従来どおり
      予約詳細ダイアログが開く(代行登録ダイアログは開かない)。
      休憩・予約不可ブロックの上をクリックしたときは代行登録ダイアログでよい
- [ ] **ドラッグ移動**: ダイアログのヘッダーをつかんで移動できる。画面外へは
      出ず、ウィンドウをリサイズしても画面内に残る
- [ ] **非モーダル**: 背景が暗くならず、ダイアログを開いたまま背後のカレンダーを
      **スクロール・日付移動(ヘッダーの ‹ › ・日付ピッカー・今日・日/週トグル)**
      できる(電話を受けながら空きを見る運用)
- [ ] **背後のクリックは無効**: ダイアログを開いている間、背後の予約カード・
      空き枠は押せない(予約詳細も代行登録も開かない)。カーソルが指マークに
      ならずホバーの影も出ない。閉じると元どおり押せる
      ※ 入力途中に別の詳細が開いてフォームが消える事故の防止(実機フィードバック)
- [ ] **その場で反映**: 登録すると画面遷移せずダイアログが閉じ、登録した予約が
      そのままカレンダーに現れる
- [ ] **フォームの日付を変えると背後が追従する**: ダイアログの「日付」欄を
      別の日に変えると、少し置いて(約0.3秒)背後のカレンダーがその日付へ動く。
      **日表示ならその日**、**週表示ならその日を含む週**になる(表示種別は
      変わらない)。すでに見えている日付・週のときは動かない。
      登録・変更の**どちらのダイアログでも**効く
- [ ] **追従してもダイアログの入力が消えない**: 上の追従が起きたあとも、
      顧客(検索して選んだ顧客・新規客名・電話)・メニューの選択・スタッフ・
      時間・ご要望がそのまま残っている。ダイアログの位置も動かない
      (ドラッグで移動していたらその位置のまま)。空き時間一覧と空き判定は
      新しい日付のものに更新される
- [ ] **手動の日付移動は従来どおり**: ダイアログを開いたままでも、ヘッダーの
      ‹ › ・日付ピッカー・今日・日/週トグルで従来どおり移動できる。
      追従で戻るボタンの履歴が増えない(追従後にブラウザの戻るを押すと、
      ダイアログを開く前の画面に戻る = 日付ごとの履歴が積まれていない)
- [ ] **Escape・×で閉じる**。スマホ幅では画面下からのシート表示になり、
      ドラッグは無効(横スクロールが出ない)
- [ ] **定休日・過去**: 定休日/過去の時間帯をクリックして開いても、
      「定休日は登録できません」「過去の時間は登録できません」で登録できない。
      予約のない定休日はタイムライン自体が無く、クリックしても何も起きない
- [ ] **空き枠クリック(週表示)**: 週表示で日付列の空いている時間帯をクリックすると
      代行登録ダイアログが開き、**日付と時刻だけ**が初期入力され
      **スタッフは「選択してください」(未選択)**になる。時刻は日表示と同じく
      `salon_settings.slot_interval_minutes` の刻みに切り下がる
- [ ] **週表示の時間軸は正時始まり**: 週内に半端な時刻(例 9:15 開始)の予約が
      あっても、時間軸の目盛りと軸の上端・下端は正時のまま(営業時間そのものが
      正時でない店舗を除く)。この状態で空き時間をクリックすると、得られる時刻が
      空き枠一覧の時刻と一致する(9:15・9:45 のようにずれない)
- [ ] **週表示: スタッフを選ぶと空き情報が出る**: ダイアログ内でスタッフを選ぶと
      「この日の空き時間」一覧と空き判定メッセージが出る(誰が空いているかは
      スタッフを切り替えて確認できる)。未選択のまま登録しようとすると
      「スタッフを選択してください」がスタッフ欄に出て登録されない
- [ ] **週表示の非回帰**: 予約カードをクリックしたときは従来どおり予約詳細
      ダイアログのみが開く(代行登録ダイアログは開かない)。定休日の列も
      クリックで開くが「定休日は登録できません」で登録できない。
      営業日が1日もない週は「この週に営業日はありません。」のままで何も起きない

### 代行登録・店側変更・キャンセル

- [ ] **代行↔客側の往復**: 管理画面で代行登録(既存顧客検索・新規電話客のいずれも)
      → カレンダーに出る → **LIFFスタブ側の日時選択で同じ枠が「埋まり」表示**になる
- [ ] 顧客検索が名前・電話の部分一致で候補を出し、選択で確定・×で解除できる
- [ ] 代行登録の空き表示(「この枠は空いています。◯分確保できます。」/埋まり)が
      スタッフ・日時・メニューに追随する
- [ ] **空き枠でない理由が具体的に出る**: 「空き枠ではありません」で終わらず、
      その枠が作られなかった理由が出る。実データで一通り確認する
      - 勤務の無い曜日のスタッフ → 「◯◯さんはこの日の勤務がありません」
      - 始業前・終業後の時間 → 「勤務時間外です(◯:◯◯〜◯:◯◯)」
      - 休憩と重なる時間 → 「休憩時間です(◯:◯◯〜◯:◯◯)」
      - 他の予約と重なる時間 → 「この時間は他の予約と重なっています」
      - 閉店間際で所要時間が入らない → 「◯:◯◯の閉店までに◯分は確保できません」
      - 直前締切内 → 「直前すぎます(◯分前までに受付)」/ 受付期間の先 →
        「受付期間(◯日先まで)を超えています」
      - 刻みに合わない手入力(例 10:15)→ 「開始時刻が◯分刻みに合っていません」
      いずれも**時刻・分数・日数はDBの営業時間・勤務時間・`salon_settings` の値**で、
      設定を変えると文面も追随すること(ADR-007)。定休日・過去以外は登録ボタンが
      押せる(店側の上書き登録)
- [ ] **その日の空き時間一覧**: スタッフ・日付・メニューを選ぶと時刻ボタンが並び、
      埋まりは取り消し線+グレーで押せない。押すと時間欄に反映される。
      空き0件なら「この日に空き枠はありません」。定休日・受付期間外も0件になる
- [ ] **手入力の上書きは維持**: 一覧に無い時間(休憩中・勤務時間外)を時間欄へ
      手入力すると「他の予約と重なっています」等の注意付きで登録できる
- [ ] **変更モードの空き時間一覧**: 店側変更で開くと、自分の旧枠が「埋まり」でなく
      空きとして一覧に出る(excludeReservationId が効いている)
- [ ] 予約ブロックをタップ → 詳細ダイアログ(客名・連絡先・日時/担当・メニュー合計・
      ご要望・スタッフメモ)。ブロック(予約不可)・休憩には詳細が無い
      (日表示ではその上をタップすると代行登録ダイアログが開く。上の節を参照)
- [ ] **スタッフメモ**: 詳細から編集・保存すると customers.note に入り、
      **同じ客の別の予約詳細にも同じメモが出る**(顧客単位保存の確認)
- [ ] **変更はダイアログ内で完結**: 詳細の「変更」を押すと**ページ遷移せず**、
      カレンダー上に変更ダイアログ(非モーダル・ドラッグ可)が開く。顧客名は
      固定表示、メニュー・スタッフ・日時・ご要望が既存予約の値で埋まっている
- [ ] **店側のご要望欄**: 代行登録・変更の自由記入欄は「ご要望・ご相談(任意)」で、
      欄の下に「お客様にも表示されうる・店内用のメモはスタッフメモへ」の案内がある。
      代行登録で書いた内容は予約詳細の「お客様からのご要望」に出る
      (店内メモ欄ではない: milestone-4-plan.md 決定5)
- [ ] **変更ダイアログから詳細へ戻れる**: **「この内容で変更」のすぐ下**にある
      「詳細に戻る」で同じ予約の詳細ダイアログに引き返せる(店側キャンセルの
      「キャンセルする / 戻る」と同じ並び)。タイトルバーには戻るボタンが**無い**
      (気づかれないという実機フィードバックで移設)。Escape・× では閉じて
      カレンダーに戻る。代行登録(空き枠クリック)には戻るボタンが出ない
- [ ] **変更ダイアログの初期位置**: 代行登録と**同じ位置ロジック**で開く =
      元の予約カードがあった列**以外**の広い領域の中央(スタッフ2人なら
      もう一方の列の真ん中)。押した列の空き状況が隠れない。ヘッダーをつかんで
      移動でき、画面外へ出ない。背景は暗くならず、背後のカレンダーを見ながら
      日時を調整できる。日表示・週表示のどちらのカードからでも同じ
      ※ スマホのリスト表示から開いた場合は列が無いので右寄せ(md未満はシート表示)
- [ ] **変更の反映**: 「この内容で変更」で遷移せずダイアログが閉じ、
      カレンダー上の予約がその場で新しい日時・担当へ移動する
- [ ] **ダイアログの排他**: 変更・代行登録ダイアログを開いている間は、
      背後のカレンダーの空き枠も予約カードも押せない(代行登録ダイアログも
      予約詳細ダイアログも開かず、入力が消えない)。上の「背後のクリックは無効」を参照
- [ ] **変更ダイアログでも日付が追従する**: 変更ダイアログで日付を別の週の日に
      変えると背後のカレンダーがその日(週表示ならその週)へ動き、
      メニュー・時間・ご要望の入力は消えない。上の「フォームの日付を変えると
      背後が追従する」を参照
- [ ] **ページ版は追従しない(非回帰)**: `/admin/reservations/new` と
      `/admin/reservations/[id]/edit` のページ版で日付を変えても、
      勝手なページ遷移は起きない(背後にカレンダーが無いため追従は無効)
- [ ] **ページ版の戻る導線**: `/admin/reservations/[id]/edit` と
      `/admin/reservations/new` を直URLで開くと上部に「カレンダーに戻る」があり、
      前者はその予約の日のカレンダーへ戻る
- [ ] **店側キャンセル**: 締切に関係なくキャンセルでき、枠が即座に空きに戻る
      (客側の日時選択で空きになる)。締切超過でも店側は操作できる
- [ ] **店側変更(UPDATE方式)**: 同じ予約を同枠のままメニュー変更・30分ずらしできる
      (自分の旧枠が「埋まり」にならない)。予約IDが変わらない(DBで確認)
- [ ] **変更の競合ロールバック**: 変更先の枠に別の予約を先に入れてから変更確定 →
      「その枠は埋まりました」になり、**元予約が担当・時間・メニューとも無傷で残る**
- [ ] **代行登録とLIFF予約の同時競合**: 管理画面の代行登録とLIFFの予約を同枠へ
      ほぼ同時に確定 → 片方だけ成功し、もう片方が23P01で弾かれる(EXCLUDE制約)

## 管理画面 設定系(M4b・ADR-005 / ADR-007)

M4bの主眼は「店側が自力で店舗固有値を変えられること」(ADR-007)。
**設定を変えたら必ず客側(LIFF)まで往復して確認する**こと。

### オーナー/スタッフの権限差(ADR-005)

- [ ] **紐付けが必須**: `staff.auth_user_id` を紐付けていないユーザーでログインすると
      設定画面が「この操作にはオーナー権限が必要です」になる(`current_staff_role()`
      がNULLを返すため)。READMEの紐付け手順を実施すると解消する
- [ ] スタッフロールでログイン → サイドバーに設定グループが出ない。
      `/admin/settings/business` などを**直URLで開いても弾かれる**
- [ ] スタッフロールでも予約カレンダー・代行登録・店側変更・店側キャンセル・
      スタッフメモ編集は従来どおりできる
- [ ] スタッフロールでもダッシュボード(`/admin/dashboard`)を開けて、数値が
      オーナーと同じ。`/admin/settings/display` は直URLでも弾かれる
- [ ] **RLSがアプリ層を迂回しても効く**: スタッフのセッションで設定系テーブル
      (`menus` / `business_hours` / `staff` / `date_overrides` など)を直接
      UPDATE/DELETE → **0行**しか変わらない。INSERT は 42501 で拒否される
- [ ] **臨時休ブロックだけはRLSで守られていない**: `reservations` は予約運用の
      テーブルなのでスタッフも書ける。臨時休の追加・削除を止めているのは
      アプリ層の `requireOwner()` だけであることを認識しておく(仕様)
- [ ] 最後のオーナーを「スタッフ」に降格・無効化しようとすると拒否される

### 未保存の変更(節ごとに保存する6箇所に共通)

対象は `settings/business` の「毎週の定休日+曜日ごとの営業時間」「第◯曜日の定休」、
`settings/staff` の「スタッフ情報(既存の編集)」「勤務曜日・時間」、
`settings/salon` の「店舗(店名)」「予約の受付ルール」。
トグル・ドラッグ並べ替え・臨時休業の追加削除は操作した時点で保存される
即時反映型なので対象外(未保存の状態が生まれない)。

- [ ] **変更していない状態では保存ボタンが押せない**: 画面を開いた直後、
      どの節の「保存する」も無効(送信中の無効化は従来どおり)
- [ ] **変更すると節見出しにバッジと変更箇所の目印が出る**: 値を1つ変えると
      節の見出しに「未保存の変更」バッジ、変えた行・項目に「変更」の目印と
      淡い下地が出る。**7曜日×時刻の表でどの曜日を触ったか追える**こと。
      勤務曜日を休みにした曜日は入力行が消えるので、チップの下に
      「未保存の変更: ◯曜日」と曜日名で出る
- [ ] **元に戻すで保存済みの値に戻る**: 変更があるときだけ出る「元に戻す」を
      押すと、props(保存済みの値)に戻り、バッジ・目印が消えて保存ボタンが
      また押せなくなる
- [ ] **値を手で元に戻しても変更なしに戻る**(正規化): 時刻を変えてから元の
      時刻に戻す / 定休の曜日を一度営業にして時刻を入れてから定休に戻す /
      店名の末尾に空白を足す / 表示順を「1」から「01」にする →
      いずれも保存結果が同じなので**変更なし**の状態に戻る
- [ ] **保存に成功すると変更なしの状態に戻る**: 保存直後に「保存しました」が
      出たあと、バッジ・目印・「元に戻す」が消えて保存ボタンがまた押せなく
      なる(`revalidatePath` で新しいpropsが降りる経路と、保存した値で基準を
      進める経路の両方が効く)。**スタッフを切り替えてから戻っても同じ**
- [ ] 上をスマホ幅でも確認する(バッジ・「元に戻す」が折り返して収まり、
      横スクロールが出ない)

### 営業日・営業時間(`/admin/settings/business`・モックE-2)

- [ ] **毎週の定休日**: 曜日チップをONにする → 管理画面の週表示が斜線になり、
      **客側の日時選択でその曜日が選べなくなる**
- [ ] **曜日ごとの営業時間**: 開店・閉店を変える → 客側の枠の範囲と管理画面
      カレンダーの時間軸が変わる。営業ONで時刻が空のままだと保存できない
- [ ] **曜日で閉店時刻が違うときの週表示**: 例「他の曜日は19時閉店・水曜だけ
      21時閉店」にする → 週表示の時間軸は 9:00〜21:00 のまま(水曜の19時以降の
      予約が消えない)で、**水曜以外の 19:00〜21:00 に営業時間外の淡い帯が出る**。
      水曜には出ない。開店が遅い曜日では開店前にも帯が出る。
      定休日の列(濃い下地+「定休日」)と帯(淡い)が濃さで区別でき、
      ダークテーマでも破綻しない
- [ ] **臨時営業・短縮営業と帯**: 定休曜日を**時刻付きで臨時営業**にした日
      (例 10:00〜15:00)は、週表示でその列が定休日にならず、**時刻の外側
      (開店前・閉店後)に帯が出る**。営業曜日に時刻付きの上書きを重ねた
      短縮営業の日も、狭まった分が帯になる
- [ ] **帯の上のクリックは従来どおり**: 営業時間外の帯の上をクリックしても
      代行登録ダイアログは開き、日付・時刻が初期入力される。スタッフとメニューを
      選ぶと「19:00の閉店までに60分は確保できません」の警告が出るが、
      **登録自体は店側の判断でできる**(電話での特別対応)
- [ ] **第◯曜日の定休**: 「第3日曜」を登録 → 補足文が設定内容から生成され、
      **その月の第3日曜だけ**休業になる(第5週が無い月の挙動も確認)
- [ ] **祝日を休業にする**: ONにすると直近の祝日が休業になる。
      OFFに戻すと営業に戻る
- [ ] **臨時休業・連休**: 期間(例 8/13〜8/16)を登録 → リストに「連休」バッジで
      1行表示され、客側で4日とも選べない。削除すると戻る
- [ ] **削除の対象が正しい**: 祝日行(自動導出)には削除ボタンが無く、
      登録データの行だけ削除できる。**削除して消えるのが狙った1件だけ**であること
- [ ] **期間の重なりを拒否**: 既存の登録と重なる期間を追加 → 23P01 を
      「その期間はすでに登録されています」として表示する(EXCLUDE制約)
- [ ] **臨時営業(祝日の打ち消し)**: 営業曜日の祝日に「営業」を時刻なしで登録 →
      その曜日の営業時間で客側の枠が開く
- [ ] **臨時営業(定休曜日)**: 定休の曜日に「営業」を登録するとき、
      **営業時間の入力が必須**になる(入力しないとエラー)。時刻を入れて登録すると
      **その曜日の勤務行が無いスタッフにも枠が出る**(M4bの運用ルール)
- [ ] **臨時営業日に出ないスタッフ**: 上の日にそのスタッフの臨時休ブロックを
      入れると、そのスタッフの枠だけ消える

### スタッフ設定(`/admin/settings/staff`・モックE)

- [ ] 勤務曜日チップをOFF → その曜日にそのスタッフの枠が客側に出なくなる
- [ ] 休憩を設定 → 管理画面の日表示に淡色の休憩ブロックが出て、
      その時間帯の枠が客側に出ない
- [ ] 休憩が勤務時間外・開始>=終了などの不正な入力は保存できない
- [ ] **臨時休ブロック**: 日付と時間帯を指定して追加 → カレンダーにブロックが出て
      その枠が客側から消える。「終日」はその日の実効勤務時間いっぱいになる
- [ ] **既存予約と重なる臨時休は登録できない**: 予約のある時間帯に臨時休を追加 →
      23P01 で「その時間帯には予約が入っています」(EXCLUDE制約が本体)
- [ ] **臨時休の削除で予約が消えない**: 削除は `kind='block'` に限定されている。
      **予約のIDを渡しても消えないこと**を確かめる。
      注意: 臨時休を普通に削除しても予約は消えないので、**それではこの項目の
      確認にならない**。削除は主キー1件を指定するため、`kind` の条件が
      あってもなくても、臨時休のIDで消えるのはその臨時休1行だけだから。
      手順: DevToolsのNetworkタブで臨時休の削除を1回実行 → そのリクエストを
      「Copy as fetch」 → UUIDを予約のIDに差し替えてコンソールで実行 →
      「対象の臨時休が見つかりませんでした」が返り、DBでその予約が
      `confirmed` のまま残っていること。
      (臨時休だけが物理削除なので、ここが唯一「予約の行が本当に消えうる」経路。
      将来 `kind` の条件を外してもテストもビルドも通ってしまう)
- [ ] スタッフを追加 → 客側のスタッフ選択に出る。無効化すると出なくなるが、
      **そのスタッフの過去・未来の予約は壊れない**
- [ ] スタッフの物理削除の導線が無い(`reservations.staff_id` が参照するため)

### メニュー管理(`/admin/settings/menus`・モックF)

- [ ] メニューを追加 → 客側のメニュー選択に出る。料金・所要時間が反映され、
      **所要時間を変えると必要な枠の長さが変わる**
- [ ] メニューを「非表示」にすると客側から消えるが、**そのメニューを含む
      過去の予約の表示は壊れない**(`reservation_menus` のスナップショット)
- [ ] メニューの物理削除の導線が無い(非表示で運用する)
- [ ] **ドラッグ並べ替え**: カテゴリ内で行をドラッグ → 客側の並び順が変わる。
      **カテゴリをまたぐ移動はできない**(カテゴリ変更は編集ダイアログ)
- [ ] **タッチとキーボードでも並べ替えできる**: スマホ実機でドラッグできること、
      ハンドルにフォーカスしてスペース→矢印→スペースで動くこと
- [ ] **カテゴリ編集**: 追加・名称変更・並べ替えをまとめて保存 →
      客側のカテゴリ見出しの順序と名前が変わる
- [ ] **メニューが残っているカテゴリは削除できない**(件数入りのメッセージが出る)
- [ ] **カテゴリ保存はトランザクションではない**(差分のある種別だけを
      更新→追加→削除の順に流す。最大3クエリで、並べ替えだけなら更新1回)。
      2種類以上が動く保存(名称変更+追加、途中への追加+並べ替えなど)が
      途中で失敗すると部分反映が残る。**残っても画面からもう一度保存すれば
      差分がDBの現在値と突き合わせて再計算されるので収束する**ことと、
      失敗時に「カテゴリの保存に失敗しました」が出ることを見ておく。
      故意に途中で失敗させるのは難しい(名前に一意制約が無く、権限不足は
      requireOwner が先に止める)ので、通信切断では「何も入らない」になりがち

### ダッシュボード(`/admin/dashboard`・モックG、M4c)

- [ ] 「今日の予約件数」がサイドバーの「今日の予約」と一致し、スタッフ別内訳の
      合計とも一致する(キャンセル済み・臨時休ブロックは数えない)
- [ ] 「今月の予約」の先月比: 先月の確定予約数との差が「+n件 / −n件 / ±0件」で出る
- [ ] **150通超の警告(ADR-002)**: `push_messages` に今月の日時でテスト行を
      151件入れる → ダッシュボードのバーと文言が赤になり、サイドバーのミニ集計にも
      「150通を超えました」が出る。150件ちょうどでは出ない。201件で
      「無料枠を超えました」。**確認後はテスト行を必ず削除する**(リモートDBへの
      書き込みなのでユーザー作業)
      Supabase の SQL Editor で実行する。M5(プッシュ送信)より前は `push_messages`
      の行がすべてテスト用なので、後片付けで消してよい。**M5 以降は実データが
      入るので、テスト行を見分けられる条件(例: 実行時刻の範囲)で消すこと**
      ```sql
      -- 1. 151件にする(警告: バーと文言が赤、サイドバーに「150通を超えました」)
      insert into public.push_messages (type, sent_at)
      select 'other', now() from generate_series(1, 151);

      -- 2. さらに50件足して201件にする(「無料枠の200通を超えました。…」)
      insert into public.push_messages (type, sent_at)
      select 'other', now() from generate_series(1, 50);

      -- 3. 後片付け(必ず実行。ダッシュボードが 0 / 200 通に戻れば完了)
      delete from public.push_messages
      where type = 'other' and reservation_id is null;
      ```
- [ ] M5 以降は前日リマインドの実データが `push_messages` に入る(`type = 'reminder'`・
      予約IDつき)。上の後片付けの条件(`type = 'other' and reservation_id is null`)は
      テスト行だけに当たる
